# Why schema serialization broke the local protocol

The v0.3 HTTP client used the same recursively sorted JSON encoding as the evidence hash chain. That changed the declared order of the response schema's `properties`. The tool branch started with `arguments`, the advice branch with `check_ids`, and only the abstention branch still started with `kind`. The prompt's examples all started with `kind`.

The diagnostic in [schema-order-4b](../receipts/v0.4/schema-order-4b/run.json) held the model artifact, prompt, settings, schema values, and all other request fields fixed. It changed only the order of each branch's `properties`. In the sequence sorted, declared, declared, sorted, the actual model returned abstain, read_snapshot, read_snapshot, abstain. No process observations, expected process answers, or tools were executed in this diagnostic. Every request and response is retained. The earlier [whole-request ordering diagnostic](../receipts/v0.4/serialization-4b/run.json) produced the same pattern.

This establishes an order-sensitive integration failure on the tested artifact and serving stack. The likely mechanism is grammar-constrained decoding: the grammar can require a property's declared position even though ordinary JSON object semantics do not. Upstream llama.cpp has a test that explicitly preserves the original property order in its generated grammar ([primary source](https://github.com/ggml-org/llama.cpp/blob/master/tests/test-json-schema-to-grammar.cpp), read 2026-09-20). That source supports the mechanism; we did not inspect the exact running daemon's compiled implementation.

The fix separates wire serialization from canonical evidence serialization. HTTP JSON preserves declaration order, with `kind` first in all three schema branches. Canonical evidence hashes remain sorted and compatible with existing logs. The client now records both the semantic request hash and the exact encoded request-byte hash, plus a wire-schema hash. The original semantic hash alone could not distinguish the two requests that caused different outputs.

The schema still permits tool requests, advice, and abstention. No refusal branch was removed, no answer IDs were supplied, and no validator, policy threshold, drill expectation, or freshness limit was relaxed. Regression tests inspect the bytes passed to the HTTP connection, including each schema branch's property order, and verify that order changes affect wire bytes while preserving semantic hashes. Non-finite JSON remains rejected.

The earlier counters named `voluntary_abstentions` count model-emitted abstention objects. They do not establish why a model selected that object. The v0.3 refusals cannot be interpreted as learned safety behavior or evidence of inability to understand the process. They were obtained through this defective transport.

The declared-order fix restores the ability to request evidence. The first corrected full runs exposed another protocol failure: models sometimes proposed advice before reading the required history or policy. A second change makes read progress explicit after every tool result. The client sends a separately receipted `protocol_state` message listing remaining required reads. After completion it asks the model to apply the policy to the values. This is orchestration metadata, not a finding, expected answer, computed trend, or simulator label. Models retain the option to abstain and the validator still rejects advice that skips a required read.

Complete assessments still need separate evaluation for supported findings, checks, and evidence. See the [v0.4 run index](../receipts/v0.4/README.md) for the actual development results and remaining limitations.
